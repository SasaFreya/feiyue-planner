# 飞跃日程规划本：桌面整合、日历与时间记录规划

日期：2026-10-13（北京时间）
状态：原规划保留作设计依据；2026-10-13 已执行主要方案。最新实施与验证状态见《产品设计想法》“执行桌面整合方案”，下文的“未实施”描述为规划时的历史状态。

## 1. 产品关系与本次纠正

目标是一个完整的飞跃日程规划本，有三个入口：桌面悬浮头像、桌面完整窗口、浏览器。三者操作同一批事项、项目和时间记录。

现状并非如此：网站的纸本条目与项目数据存于本机 D1 / SQLite 预览库；Swift 悬浮原型把每日清单另存为 JSON，尚未接入网站。原型只能用于确认悬浮交互，不应继续扩展成另一套规划本。

原来的年 / 月 / 周纸本、年度纵览、自由页、拖动与撤销、项目与任务池、动态安全线、自动分配、今日随记、回响之书、导出、设置与反馈都要保留。网站已有统计基于预计工时；新的实际计时需另建记录，旧数值不能冒充实测时间。

## 2. 桌面使用流程

### 悬浮头像与小清单

- 头像可拖动、记住位置；点击展开今日事项。
- 外圈仍代表今日完成事项比例，空清单为 0%，与计时分开。
- 每行：完成框、事项名称、项目彩色圆点、累计用时、开始 / 暂停。
- 下方快速添加事项；点项目圆点可选择项目。
- 正在计时时头像附带小标识或短时长，保持纯色，不加渐变或毛玻璃。
- 明确的「打开完整规划」按钮进入大窗口；收起小清单不会暂停计时。
- 建议环统计当天全部有效事项，项目筛选只影响列表，并保留总数说明；未安排事项留在任务池。

### 完整窗口

借鉴用户截图的桌面工作台结构，默认三栏：

| 区域 | 内容 |
| --- | --- |
| 左侧导航 | 今天、日历、纸本规划、项目、时间记录、回响与导出；下方设置与反馈 |
| 左侧项目列表 | 彩色圆点＋项目名称，支持显隐筛选、管理项目 |
| 中间主区 | 原来的纸本或 FullCalendar 日 / 周 / 月 / 年 / 列表，以及对应统计页 |
| 右侧可收起详情 | 编辑选中的事项、项目、计划起止时间、预计时长、实际用时、计时明细 |
| 持续可见的计时条 | 当前事项、已用时、暂停、跳到详情 |

“GUI”就是这个可点击、可编辑的图形界面。截图用于参考窗口组织方式；本轮没有提出聊天助手或 AI 对话功能。

## 3. 原纸本与 FullCalendar

原紙本保留为「纸本规划」，新增「日历」入口。两种视图引用同一事项 ID：移动、编辑、完成一次，其他视图立即更新。自由随记、月度目标等仍按自身结构保存，不强行转成定时事件。

FullCalendar 用于：

- 日：一天的时间轴、全天事项。
- 周：七天时间轴，拖动更改安排，拖动边缘调整计划时段。
- 月：月格与项目颜色，点击空白新建，点击事项查看详情。
- 年：全年多月总览；原年度纵览表同时保留。
- 列表：按日期列出安排，便于检索。

日历拖动只改变计划，不修改已发生的时间记录。没有具体时间的事项显示在全天区域；未安排事项在任务池。计划时段长度、预计工作分钟、实际投入是三个独立值。

选用 FullCalendar 标准功能即可覆盖本轮；官方文档列出了上述视图及拖动缩放，非 Premium 插件使用 MIT 许可。资源排班时间线不在本轮需求内。

## 4. 计时行为（建议默认规则）

- 开始：给当前事项创建一个计时片段；暂停：结束片段；继续：创建下一片段。总用时为片段之和。
- 同一时刻只计一件事。开始另一件时，在同一事务中暂停上一件，避免窗口之间重复累计。
- 勾选完成会停止该事项正在进行的计时；取消完成保留历史用时。
- 收起小窗、关闭大窗口继续计时，只要应用还在运行。明确退出应用默认先保存并暂停。
- 电脑睡眠自动暂停，唤醒后由用户继续。异常退出后以最后保存的心跳为恢复边界，标注“待核对”，允许修正，不把未知离线时间全部计入。
- 支持手动补录、改起止时间和删除错误片段，保留修改记录；发现重叠时提示并阻止不经处理的重复累计。
- 运行状态由统一数据服务保存，界面的秒数只是显示；不能只靠某个窗口的定时器加一。
- 时间点保存为绝对时间，统计默认 Asia/Shanghai，周一为每周开始；跨午夜、跨月的片段按边界拆分统计。

示例：09:00–09:25 与 10:00–10:15 两段合计 40 分钟，中间暂停不计入。

## 5. 时间记录页面

顶部有两组独立切换：

1. 时间范围：日 / 周 / 月 / 年 / 自定义起止日期，并有上一期、下一期、回到本期。
2. 汇总方式：按具体事项 / 按项目。

「按事项」显示日期、事项、项目、实际投入和片段详情；「按项目」显示项目色、合计时长、占比，并可展开到事项和具体计时片段。未归属项目的事项进入「未分类」。

自然周 / 自然月 / 自然年与“近 7 / 30 / 365 天”不同，页面用明确的起止日期展示。总计仅累加范围内片段的交集；正在计时部分显示“计时中”，实时值与已保存记录有清晰状态。

统计主值使用实际用时，另可对照预计用时、完成数和趋势。两种汇总方式的总时长必须一致；筛选与导出使用相同口径。

## 6. 项目圆点与自定义

本轮把“项目字段增加、删减、自定义”先解释为可自定义所属项目的选项，如论文、学习、工作、生活。

- 点事项旁的颜色圆点：弹出项目选择器，可搜索、选项目或「＋新建项目」。
- 管理项目：改名称、换颜色、排序、归档；可选春日五色，也能自定义纯色。
- 左侧项目勾选用于控制日历显示；换色同步到日历、清单与统计，并始终显示名称，不能只靠颜色辨别。
- 删除项目时默认提供归档；确需移除则先让用户选择将事项迁移到另一项目或未分类，不连带删除事项和时间记录。
- 已有截止日期、安全线等能力继续保留。日常分类可不设截止日期，不参与需要截止日期的安全线分摊。
- 项目改名或换色不改变 ID；事项重新归属项目时，建议既有片段保留发生时的项目归属，未来片段按新归属，另提供显式的历史重分类操作。
- 任意新增“优先级、地点、标签”等字段作为扩展设想记录。先交付项目选项管理，再设计通用字段编辑器，避免把本轮的项目分类误做成复杂表格系统。

## 7. 复用代码与统一数据的技术方案

建议使用 Electron 作为正式桌面外壳，复用现有 React 界面。它适合同时提供完整窗口、无边框悬浮入口、菜单栏与本地文件存储，代价是安装体积和内存较高；Tauri 可作为后续体积优化方案。此项是技术建议，尚未引入依赖。

现有 Next / vinext 路由依赖 Cloudflare 环境，不能直接打包网页就声称离线可用。需要先抽出共享领域逻辑及数据接口：网页界面通过统一接口读写；桌面主进程负责本地 SQLite、计时协调、休眠处理与窗口事件。渲染进程只获得最小受控接口。

数据结构建议：

- Project：稳定 ID、名称、颜色、可选起止日期、归档状态。
- Task：稳定 ID、标题、所属项目、预计分钟、完成状态。
- Schedule：事项 ID、日期或计划起止、全天标记、纸本放置位置。
- TimeSession：稳定 ID、事项 ID、发生时项目 ID、开始 / 结束、来源、修正状态。
- PaperNote / Goal：原纸本随记、自由文字、月目标、年度记录，保留各自语义。
- TimerState：唯一活动计时片段、最近心跳、版本号。

现有项目保存使用整份 workspace JSON PUT；多窗口各自保存会覆盖对方更新。正式整合需改成按实体更新、版本校验和事务，并由同一个数据服务向所有窗口广播变化。

本机阶段：桌面大窗口、小窗、头像共用数据库。浏览器若继续作为可编辑入口，需要通过仅监听本机且有来源验证和会话凭据的桥接访问同一数据服务；不能继续让旧 D1 副本与新 SQLite 各写各的。旧本机网站入口在迁移后提示改用统一入口。

跨设备阶段：网站与桌面要共享云端同步协议、账户和冲突处理；当前未发布的网站不能被描述为已经云同步。本轮先解决本机统一、离线启动，跨设备同步另列后续阶段。

## 8. 迁移与实施顺序

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 1. 统一桌面与原功能 | 可双击的正式桌面包、大窗口复用原页面、小窗接共享数据；修复启动问题 | 无需手动终端或开发服务器；旧年 / 月 / 周与全部已开发入口可用；两窗口修改立即一致 |
| 2. 数据迁移与项目分类 | 稳定事项 ID、纸本关联、项目圆点选择器、统一写入 | 原纸本、项目库、悬浮 JSON 都有备份；映射可重复执行且不重复导入；拖动不切断计时关联 |
| 3. FullCalendar | 日 / 周 / 月 / 年及列表、事件详情、项目筛选 | 纸本与新日历对同一事项的修改一致；随记和目标不丢失；保留撤销 |
| 4. 开始 / 暂停 | 多片段计时、单活动任务、退出与睡眠保存、异常恢复 | 25＋15 分钟等于 40 分钟；多窗口开始不重复计时；关闭大窗不会中断 |
| 5. 时间记录与交付验证 | 日 / 周 / 月 / 年 / 自定义范围，事项 / 项目切换，明细修正与导出 | 跨日切分正确；两种汇总总量相等；补录修正后同步更新；重启恢复与离线完整运行 |

阶段 1 和 2 的共享数据底座应一起打通后再交付，不能发布另一份独立清单。建议先交付一个可用的小闭环：旧功能进入大窗口＋小窗同数据＋项目圆点＋单事项计时，然后补齐各类日历和统计。

迁移先备份三种现有来源，生成来源 ID 映射和数量核对。原纸本没有稳定事项 ID，按来源位置建立初始关联；同名条目不自动合并；随记不转成任务；旧分钟保留为预计值；原悬浮 JSON 导入时保留日期和完成状态，且允许回滚。切换完成后只保留一个写入源。

## 10. 新增：拖拽调整每日执行优先顺序

用户明确要求：可以拖拽每日事件进行优先级调整。状态：已纳入规划，尚未实现。

- 今日清单（小窗与大窗口）提供拖动把手，向上 / 下移动决定先做什么，松手后保存；两个窗口同步，重启保持顺序。
- 默认使用「手动顺序」，可提供「按计划时间」「按重要程度」视图。非手动视图不允许悄悄覆盖人工顺序，用户切回手动后恢复原顺序。
- 手动顺序和高 / 中 / 低重要程度分开存储。拖到第一位不自动标为高优先级；若后续需要高 / 中 / 低标记，用单独控件设置。
- 列表内上下拖动仅改当日执行顺序；日历拖到其他日期 / 时段才改变计划安排。正在计时的事项可以换顺序，计时不中断、不新建重复记录。
- 已完成事项进入单独分区，保留原顺序信息；取消完成恢复原位置。新事项默认追加到未完成列表末尾。
- 项目筛选后的拖动只重排可见事项在全量列表中的位置，隐藏事项相对顺序保持；提供撤销本次排序。
- 键盘和菜单提供“上移 / 下移 / 置顶”作为拖动替代，长列表支持边缘滚动。
- 建议数据结构：DailyPlan(date, orderedTaskIds, revision)，任务详情仍按 ID 只存一份。移动日期时原日期移除 ID、新日期追加 ID，事务完成。计时只引用 taskId，与列表位置无关。
- 验收：拖动 C 到 A 前，刷新 / 重启后仍是 C、A、B；大窗与小窗相同；拖动不改变计划时间、项目或累计用时；过滤、完成 / 撤销完成和撤销排序不丢事项。

## 11. 自己做、借鉴还是直接用开源软件

建议：继续维护飞跃产品，复用成熟组件，按需学习完整开源应用。不要因参考项目采用 Angular 就重写现有 React 页面，也不要把整个外部项目当作可直接嵌入的功能库。

| 路径 | 适用情形 | 当前取舍 |
| --- | --- | --- |
| 直接用 Super Productivity | 首要目标是马上使用成熟任务与计时工具，能接受其既有交互 | 可作为体验对照；是否满足个人工作流要实际试用，不声称已覆盖纸本或悬浮需求 |
| Fork 并改造完整项目 | 试用后大多数功能与界面都合适，只需少量调整，愿意跟进上游 | 目前不推荐直接切换：要迁移飞跃纸本界面、旧数据并维护另一套技术栈 |
| 飞跃＋成熟组件＋参考设计 | 重视已有纸本结构、个人头像悬浮入口、统一规划与计时 | 推荐；需要自己负责迁移、持久化与计时准确性，不能只拼界面 |
| 所有功能从零手写 | 学习性实验或组件无法满足的特别需求 | 日历、基础拖动等不值得重复实现 |

具体复用安排：

- FullCalendar：日 / 周 / 月 / 年与列表日历、时间格交互。
- dnd-kit：项目已经使用其 core；每日排序采用匹配版本的 sortable 能力，复用键盘、触屏和拖动反馈。
- Electron：正式桌面外壳的建议选型，提供窗口和菜单栏；手机不由 Electron 直接生成，移动端适配与封装另算。
- Super Productivity：学习任务 ID 引用、计划与截止时间区分、计时状态流转、历史记录与本地存储；本轮未复制源码。
- 自己实现：飞跃纸本布局与数据兼容、头像交互、项目圆点、统一数据服务以及个人需要的统计展示。

### 参考材料的核对与纠正

用户粘贴的“视频生产队列 / Python＋Tkinter”分析属于其他背景。本仓库实际是 React＋TypeScript 网页和 Swift 桌面原型。不能把粘贴材料中的反问视为要求抓取视频工具代码或开展无关工作。

按功能组织代码值得采纳，但模块之间仍有依赖，不能承诺删一个文件夹就安全移除功能。建议在实际改动时逐步分出 tasks、daily-plan、calendar、paper-planner、projects、time-tracking、reports、storage 和 desktop-shell；先定义接口，不一次重排整个仓库。

截至本次官方仓库核对：Super Productivity 主仓库使用 MIT；任务模型的 TaskPriority 是 1 | 2 | 3 类型，并兼容历史字符串，不是粘贴材料所称的 enum。任务模型还从 plugin-api 引入字段，因此仅读一个 task.model.ts 不能断言读完了全部定义。若复用代码，应记录具体版本、保留许可声明，并核对相关文件与依赖的许可。

“时间统一用数字”也应细分：绝对时间点可用毫秒时间戳或带时区 ISO 时间，全天日期保持 YYYY-MM-DD，时长显式标单位。用户材料中的 timeSpent 秒数示例未核验，不能直接据此做数据迁移。飞跃建议内部片段起止用 epoch 毫秒，计算差值为毫秒，汇总显示时再转分钟 / 小时；实际统计从片段派生，不同时维护三套可独立写入的总量。

### 调整后的优先交付

第一批：统一大窗与小窗的数据，保留旧入口，加入每日拖拽排序、项目圆点与可靠的开始 / 暂停。第二批：FullCalendar 多视图与原纸本关联。第三批：完整周期统计、历史修正与导出。排序与计时的持久化、多窗口一致性需在第一批验证。
