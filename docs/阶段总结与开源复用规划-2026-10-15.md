# 飞跃日程规划本：阶段总结与开源复用规划

日期：2026-10-15。性质：现状盘点、公开资料调研与后续建议。本轮只更新文档，未安装新依赖、复制外部源码、修改业务、打包或发布。

## 1. 产品定位与当前判断

飞跃是个人桌面日程本：悬浮小球用于快速打开清单，清单用于执行，完整窗口用于规划和回顾。核心流程是「先记下来 → 安排日期或时段 → 开始/暂停 → 日历呈现实际时间 → 按事项/项目回顾」。春日纯色、纸本留白和精巧交互继续保留。

建议继续维护现有 React + TypeScript + Electron 产品，直接使用成熟组件解决日历、拖动等通用问题，参考完整开源应用的业务设计。现阶段整套换成另一款产品，会重新承担界面定制、数据迁移、计时兼容和桌面入口改造的成本。

网站界面和桌面软件是同一产品的不同入口。本机浏览器、完整窗口、小清单通过同一本机服务访问 SQLite；这并不意味着已经具备跨设备同步。预览地址 17865 目前还依赖安装版提供的 17863 数据服务。

## 3. 下一轮实施顺序

以下均为建议待实施，未承诺完成日期。每批交付可试用的预览，并更新设计记录。

### 第一批：计时和数据可靠性

1. **备份与恢复闭环。** 设置中展示数据位置、最近成功备份、导出和恢复入口。恢复前先备份当前数据；检查格式、结构版本、任务引用及计时记录；先显示备份日期和数据量，再由用户执行恢复。先做整份恢复，不做含糊的自动合并。
2. **修正快照与提交的一致性。** 当前 `desktop-shell/store.ts` 在 SQLite COMMIT 前写 `latest.json`，并在快照后才追加 applied 操作标识。若后续数据库写入失败，快照可能领先于实际提交。这是代码检查发现的风险，未在用户数据上复现。建议从已提交状态生成快照并标注状态版本；快照失败单独记录/重试，不把已经提交成功的操作误报为保存失败。
3. **后台计时由本机服务负责。** 以持久化起止时间、剩余时长为依据；界面负责展示。倒计时截止在服务层落实，界面隐藏或节流不应影响结束时刻。明确睡眠暂停、正常退出暂停、异常重启待核对的规则。
4. **让版本和保存状态可见。** 区分安装版和预览版，显示界面/服务版本及待保存或失败状态；让预览启动可诊断，避免服务未开时表现为空白。

验收：临时数据库完成导出—恢复且任务/笔记/计划/历史时段一致；损坏文件不覆盖原数据；模拟写入及快照失败；两窗口切换计时不重复累计；隐藏窗口到期、睡眠、强退重开、跨午夜均有记录。当前每日快照是当天首次使用时保存的状态，不是每晚定时备份；同盘快照不等于异地保管。备份保留策略和外部位置可选项需一并设计。

### 第二批：把已做功能整理得更精致

1. 日历右栏保持“当天内容在上、项目事项在下”，减少重复框线和操作按钮；大窗口允许调整栏宽，小窗口改为单栏/详情抽屉，避免硬挤成细列。
2. 保留小清单的名称、完成、项目点、拖动、计时与数字；详细字段继续在完整窗口。检查长名称、倒计时菜单和完成分区，不靠增加大卡片解决。
3. “以后再安排”保持清楚的使用路径：无日期先收集，点按钮或拖入日历才安排；安排后从待定集合移出，仍是同一条事项。
4. 日历短记录继续保持可点击、可查看真实秒数；最小视觉高度不改变真实时长。密集时段、长标题和大量事项应有可发现的展开方式。
5. 统一“预计用时”和“实际用时”的表达与跳转；容量工具保留，避免另建一套实际统计。
6. 逐步归并重复样式和旧页面适配；每次整理一个功能，保留原数据映射与导出能力。

验收：350×480 清单及窄/宽主窗口无横向溢出；鼠标/键盘完成排序；右栏任务拖入月历后，今天、周历和计时归属一致；长标题、5 秒片段和多条同时间记录能读取详情。任何验收数据使用临时库。

### 第三批：基础稳定后增加复用率高的能力

- 周期事项：每周课程、每月回顾；支持仅改这一次/整个系列和跳过一次。重复规则生成计划实例，不能直接生成“已发生”的时间记录。每个实例独立完成、计时。
- 常用项目模板、周回顾：减少重复录入，先从真实使用中提取模板。
- 真正的任务下子任务、自定义字段：仍是待细化需求，先保持现有项目下事项可用。
- 可选自动活动回顾、丰富头像动作、手机/云同步、登录自启、公开演示/开源：未来评估，当前不扩展实施。

## 5. “自己做”和“拿来用”的分工

- **直接复用组件：** 日历引擎、拖动机制、可调整分栏、后续重复日期计算。复用时保留许可证和版权说明，锁定适配版本。
- **借鉴完整软件：** Super Productivity 的任务/计时工作流、solidtime 的时间回顾组织、ActivityWatch 的可选活动记录思路。借鉴不等于复制全部源码或引入第二套数据源。
- **继续维护飞跃自己的规则：** 小清单审美、笔记与旧数据兼容、一份任务驱动多个入口、计划与实际分离、数据迁移及恢复。它们决定产品是否符合当前使用习惯，通用项目不能直接代替。

不需要为当前备份功能再引入一套任务应用或同步后端。先用现有 SQLite、文件快照和 Zod 校验把恢复做完整；以后确有跨设备需求再评估同步冲突、加密和服务成本。MIT/BSD、MPL、AGPL 的复用要求不同，实际复制/分发时按具体版本与文件保留声明并核对义务，不能将“开源”视为没有条件。

## 6. 实施与发布边界

下一批建议范围锁定为「可靠计时 + 可恢复数据」，随后整理界面，再考虑周期任务。新候选一次验证一个明确场景，避免同时换日历、状态管理和存储。

当前只做本机私有试用。源码构建流程会把旧本机数据作为迁移 seed 写入构建目录；任何未来公开分发前必须分离个人迁移数据与空白发行包。以后开源/演示的想法不构成本轮上传或公开授权。

每批记录：修改内容、源码/预览/安装版状态、验证结果、未验证项、回退方式。用户明确要求时才生成下一份安装包。
